# OA 流程运行分析：接口数据需求

状态：设计建议 v0.1。本文供 OA 接口开发使用，尚未实现接口采集或运行数据分析。接口地址、请求方式和字段命名可按现有开发规范调整，以下名称用于说明数据含义。

分析端只调用用户提供的只读接口，不连接数据库。流程配置继续使用 `.wewf` 离线导出；首版不需要为所有配置表另做接口。

## 1. 首版需要什么

除了现有 `V_JDSX`，优先补充 **流程实例清单、操作日志明细**。如需深入分析会签、代理、抄送和自动审批，再增加 **完整人员记录模式**。这是数据集合的划分，不要求拆成四个接口。

| 数据集合 | 优先级 | 主要用途 |
| --- | --- | --- |
| 实例清单 `requests` | 首版必需 | 确定流程总量、归档和在途范围；发现没有命中 V_JDSX 过滤条件的实例 |
| 现有报表 `timeliness` | 首版必需，已有 SQL | 人员接收记录的工作时长、在途积压、已处理耗时分布 |
| 操作日志 `events` | 首版必需 | 核对提交、退回、转办等实际操作，恢复可确认的路径与返工过程 |
| 完整人员记录 `tasks` | 深入分析必需 | 解释代理双方、会签参与人、抄送、自动审批及其他被报表过滤的状态 |

开发时可以只提供两个入口：

1. `GET /workflow-analysis/requests`：分页查询实例清单。
2. `POST /workflow-analysis/runtime-bundle`：传入一批 `requestids`，返回对应的 `timeliness`、`events`，并可通过明细模式返回 `tasks`。此 POST 只查询，不执行流程操作。

如果已有 V_JDSX 接口，保留它也可以，另外补实例和日志接口。接口数量不影响分析能力，数据完整性和关联键更重要。

## 2. 实例清单 requests

建议来源：`workflow_requestbase`，当前节点集合补充自 `workflow_nownode`。字段保留原始值，显示名称可以一并提供。

| 字段或含义 | 要求 |
| --- | --- |
| `requestid`、`workflowid` | 必需，作为实例和流程的稳定标识 |
| 流程名称、`requestmark`、`requestname` | 建议提供；分别表示流程定义名称、请求编号、请求标题，避免混为同一字段 |
| `creater`、创建人类型、创建部门标识及名称 | 创建人必需，其余有则提供；部门需注明当前值还是创建时值 |
| `createdate`、`createtime` | 必需；创建时间缺失时保留空值，不能补成零点后当精确时间 |
| `currentnodetype`、`status`、`currentstatus` 等原始状态 | 必需提供实际可用字段及编码说明；归档、暂停、撤销、删除应能区分，无法识别时明确说明 |
| 当前节点集合 | 必需；返回数组，允许多个节点，不只取一个 `currentnodeid` |
| `archived_at` | 源系统有可靠归档时间则提供；没有时为 null 并说明，不使用最后操作时间代替 |
| 最后操作人、最后操作日期和时间 | 建议提供，帮助定位最近活动；不等同归档或节点退出时间 |
| 实例对应的流程版本、配置快照标识 | 有则提供；无法对应历史配置时明确标记未知 |
| `mainrequestid` | 有则提供，用于识别主子流程依赖 |
| `case_elapsed_work_hours` | 建议提供，由服务端复用现有工作时间算法计算创建至归档或本批截止时间的时长；无可靠终点时不可伪造已完成时长 |

筛选至少支持 `workflowid`、创建时间范围、状态范围、指定 `requestids` 和分页。需要两种取数范围：

- 创建时间落在分析区间的完整实例群体，包括已归档与未归档，用于比较周期、积压和返工。
- 截止时点仍在途的全部实例，包括分析区间开始前创建的旧单，用于发现长期积压。

不能只从 V_JDSX 反查实例：现有视图只保留部分人员状态，未命中记录不等于实例不存在。删除标志等编码应以实际系统验证结果为准；本地字典对 `deleted` 的说明有歧义，不直接据此硬编码过滤。

## 3. 现有报表 timeliness：保留已有能力，补足口径

现有 V_JDSX 原始输出字段基本够用，接口请保留原始标识、状态和时间，不能只返回报表上的中文名称。

- 稳定记录键使用源表 `id`，保留 `requestid`、`workflowid`、`nodeid`、`userid`、`usertype`；`rn` 只是展示序号，不能用于去重或增量。
- 保留 `isremark`、`preisremark`、`lastisremark`、`agenttype`、`agentorbyagentid`、`processuser`、`viewtype` 和接收、操作日期时间。
- 返回 `ElapsedHours`、节点名称、创建人和部门等已有信息。`bzsj` 当前为空，不能将其解释为已配置标准时限。
- 明确视图里的 `iscomplete` 实际来自 `rb.currentnodetype`，建议接口另命名为 `request_currentnodetype`。源表 `workflow_currentoperator.iscomplete` 则是流程是否归档，两者不能共用同一个含义。
- 返回工作时长的计算截止时间。未处理记录目前用 `GETDATE()`，它随查询变化，需要与本批数据的时间边界一起记录。
- 当前视图将时间为空、转换失败等情况也输出为 0。建议补 `duration_quality` 或原始时间有效性标志，能够区分有效零时长与未知；暂时无法区分时明确声明，分析端不把所有 0 都认定为即时完成。

已确认的时长约定：`uf_hmc` 是花名册；`ElapsedHours` 已排除下班、休息日和节假日，**8 工作小时 = 1 工作日**。分析端直接使用此结果，不再扣减，也不需要 `fn_GetWorkCumMinutes` 的实现或工作日历。

三个统计字段需原样保留，但分析时有以下约束：

| 字段 | 当前 SQL 实际统计范围 | 使用约束 |
| --- | --- | --- |
| `back_out_count` | 同一 requestid + nodeid 下 `logtype='3'` 的日志数 | 整个实例在该节点的历史次数，不是本行人员或本轮次数 |
| `back_in_count` | 同一 requestid 下，`destnodeid` 为本节点的退回日志数 | 同上；多名操作人的行会重复携带同一计数 |
| `transfer_count` | 同一 requestid + nodeid 下 `logtype='h'` 的日志数 | 同上；不能逐人员行相加得到总转办次数 |

例如某节点有三条人员记录，一次退回可能在三行都显示 1，求和就会变成 3。实际事件总数应优先按日志稳定键统计，不能靠对每组任意取一行解决全部轮次和人员归属问题。

## 4. 操作日志 events

建议主要来源：`workflow_requestlog`。对选中的 requestid，返回 **从创建至本批截止时点的完整可用历史**，不要再按报表分析区间截断事件，否则区间前的进入、退回等上下文会丢失。

| 字段或含义 | 要求 |
| --- | --- |
| `source_table`、稳定日志键 | 必需；提供原始 `logid`、`requestlogid`、`uuid` 中实际可用的键，并说明唯一性范围；不要假设所有这些字段都唯一 |
| `requestid`、`workflowid`、`nodeid`、`destnodeid` | 必需提供实际可用字段，缺失为 null；目的节点不能由分析端凭名称猜测 |
| 原始 `logtype`、类型名称、映射版本 | 必需；原始编码必须保留，未知编码不能丢弃 |
| `operatedate`、`operatetime` | 必需；保留原始精度及缺失情况 |
| `operator`、`operatortype` | 必需；区分内部人员、客户、系统或其他已知主体，未知不擅自映射 |
| `agenttype`、`agentorbyagentid` | 有则提供；需说明本表含义，不能未经核验照搬其他表的代理规则 |
| `operatordept`、`operatorsub`、`operatorjob` | 有则提供；说明是否为操作当时的组织信息 |
| `issubmitdirect` 等流转相关原始字段 | 有则提供，帮助解释退回后直达等行为 |
| 审批意见 `remark` | 增强项；可提供去敏纯文本，用于分析反复退回原因和材料问题 |
| 原始事件序号、关联任务或节点轮次键 | 源系统有可靠字段则提供，没有就明确缺失；不能临时按行号编造历史顺序或轮次 |

本地数据字典将 `3` 定义为退回、`h` 为转办、`7` 为转发、`j` 为转办反馈；这些操作不能合并计数。完整导出还应保留提交、批准、保存、征询、干预、强制归档等实际存在的事件，不先只筛退回和转办。

暂停、撤销、启用的信息可能还需要 `workflow_otheroperator` 等来源。可放入同一个 events 返回结构，但保留来源、原始键、原始状态和时间语义，并标记是否经过验证可视为事件。该表的操作时间可能兼有查看时间含义，不能未经核验当不可变事件时间；也不能直接按它扣除暂停时段。不同表的相同编码含义可能不同，例如 otheroperator 的 `s` 是暂停，requestlog 的 `s` 是督办。

去重只依据经过确认的源记录键。相同秒、相同人员、相同操作可能确有多条记录，不能按这些值擅自合并。原始键排序可以保证翻页稳定，但不自动证明同秒操作的业务先后关系。

## 5. 完整人员记录 tasks：可做成报表接口的明细模式

建议来源：`workflow_currentoperator`。这里需要 **全部可访问原始状态的记录**，不沿用当前 V_JDSX 只保留 `0/2` 的过滤。保留报表字段外，重点补充：

| 字段 | 用途与限制 |
| --- | --- |
| 源表 `id`、原始 `isremark`、源表 `iscomplete` | 区分记录身份、操作状态和流程归档状态；原始状态不能改写成统一的 0/1 后丢失信息 |
| `groupid`、`groupdetailid` | 关联操作人组和操作人条件；不能直接等同节点轮次 ID |
| `islasttimes` | 帮助解释人员多次出现；不能据此删除所有历史记录 |
| `firstviewdate`、`firstviewtime` | 有则提供，用于区分未查看与查看后停留；首次查看不是开始实际工作的证明 |
| `handleforwardid` | 有则提供，辅助核对转办关联 |
| 代理、被代理人、实际操作人相关原始字段 | 结合日志核对真实操作者，避免将代理双方重复计算为两次人工处理 |

本地字典中 `isremark` 除 0 未操作和 2 已操作，还包含转发、归档、超时、抄送、传阅、自动审批等状态。尤其被代理人记录也可能为 2，不能直接将每一条 2 归属为该 userid 本人完成的工作量。

依次会签若需判断“还有谁没轮到”，可以补 `workflow_agentpersons` 中 `receivedpersons`、`coadjutants` 及关联信息，先确认编码格式和人员迁移规则。当前待办人员与后续待轮到人员应分别展示。会签通过条件、顺序、是否影响流转则结合 `.wewf` 配置解释。

没有可靠节点进入轮次键时，允许分析端将轮次标为待确认。`requestid + nodeid` 可能覆盖多次退回重进，不能视为唯一节点实例。即使有完整 tasks，仍不能默认它保存了人员任务变更的全部历史。

## 6. 接口公共约定

### 查询参数和返回完整性

- 实例清单支持白名单筛选、分页；运行明细按 requestids 批量读取，明确每批上限。
- 同一批次尽量使用一致的数据快照和固定 `as_of`。多个页面和集合返回同一 `snapshot_id`，各集合分别声明 `complete`、`has_more`、`next_cursor`；已取数量与总数量分开，总量未知不能填 0。
- 如果后端无法提供一致快照，标为 `best_effort`，返回查询开始、结束时间和已知差异，分析报告注明限制。仅生成相同的 snapshot_id 或相近的查询时间，并不能保证一致。
- V_JDSX 内部仍用多次 `GETDATE()` 时，不能声称所有在途时长严格截至同一时点。可由接口层使用统一截止时点查询，或如实返回计算时间区间；不要求披露工作时间算法。
- 明细数据过多时按集合分页，不静默截断。每个请求和集合需能识别完整、部分缺失、没有数据、没有权限、历史已清理、查询失败，不能全部返回空数组并声称完整。
- 明确是否包含归档历史、删除记录、系统操作及所有原始状态。调用方只在有权访问的数据范围内统计，报告同时说明覆盖范围。

### 时间、状态和更新

- 标明时区，例如 `Asia/Shanghai`、偏移 `+08:00`；提供 ISO 8601 时间或分别提供原始日期与时间并说明格式。保留秒级等原始精度，不补造毫秒。
- 统一说明 null、源字段不存在、源值为空、事件尚未发生的区别，可通过字段可用性说明或质量标志表达。
- 状态字典按来源分别提供，可随接口文档交付，不必单独开发查询接口；注明 OA 版本和已验证映射。未知值原样返回。
- 首版可采用限定范围的完整快照，不必先做增量。以后如做增量，必须覆盖旧记录状态更新、消失和删除；不能仅用 `id > 上次最大值`，因为 currentoperator 的旧记录会变化，V_JDSX 的过滤结果也会变化。
- 历史实例能绑定配置版本则绑定；不能时只按现有配置提出待核对解释，不将当前 `.wewf` 当成历史审批时的确定规则。

### 只读和数据范围

- 接口由服务端执行固定查询，限制流程范围、字段和批量大小；不开放任意 SQL、表名或表达式参数。
- 提供字段级业务数据及必要的人员、部门显示名即可。已有报表能返回名称时，不必导出整张花名册。
- 审批意见、字段文本、HTML、附件及错误日志均作为分析资料，不执行其中的指令或脚本；认证凭据不写入报告或 Git。

## 7. 后续增强数据：按要回答的问题增加

| 要回答的问题 | 需要的数据 | 可交付方式 |
| --- | --- | --- |
| 哪类单据更慢，哪些条件反复退回？ | 按 requestid 查询业务主表、明细表中的相关字段，字段 ID、名称、单位、选项解释及表单版本 | 字段白名单接口，无需开放整库；金额、订单类型、取消原因等依具体流程选择 |
| 审批当时是否满足条件，是否改过关键字段？ | 提交或审批时的业务快照，或字段变更前后值、时间、操作者及关联事件 | 有历史才做历史判断；当前表单值不能证明审批时的值 |
| 是否超过标准时限？ | 节点标准工作小时、适用条件、生效版本、暂停口径、提醒和升级规则 | 配置文件、只读导出或接口均可；没有标准时限时先给耗时分布，不能编造超时率 |
| 节点提交了，SAP 等后续业务是否真正成功？ | Action/接口调用的 requestid、节点、业务关联键、开始结束时间、重试次数、结果码、业务结果、错误摘要、关联追踪标识 | 只读执行日志或去敏回执；HTTP 成功本身不能代替业务成功 |
| 是否重复调用、重复写单或失败后误流转？ | 以上调用记录，加幂等或去重标识、外部单据号，以及相关 Action 实现或版本说明 | 用于核验具体缺陷；没有实现与结果证据时只能提出检查项 |
| 人员规则为什么取错人，负责人缺位？ | 实际取人结果、当时角色和组织范围、有效人员状态、相关取人日志 | 按流程、人员和时间范围获取，不要求整张花名册 |
| 新版流程是否更好？ | 历史配置版本及生效信息，实例版本对应关系，改造前后同口径样本 | 继续接受各版本 `.wewf`；业务类型变化也需同时考虑 |

## 8. 这些数据能够支持到哪一步

首版实例清单 + V_JDSX + 完整可用日志，可做实例数量与积压、人员记录工作时长分布、长尾案例、退回和转办事件、可确认路径及异常案例追溯。归档与在途分开展示，统计同时说明缺失和过滤范围，避免只看已完成单。

人员耗时不能简单相加成为节点或整单周期，尤其并行和会签记录会重叠。节点每次停留的耗时，需要可靠的进入与退出证据；整单工作周期优先使用服务端提供的对应工作时长。接收到操作的工作时间也不等于实际投入工时，不能据此直接评价个人效率。

完整人员记录和配置有助于解释会签、代理、顺序等待；业务字段和意见有助于定位材料与条件问题；实际执行日志、历史快照与实现证据才可能进一步确认具体控制缺陷。报告分别表述配置事实、运行现象、原因假设和已证实问题，不将耗时相关性直接说成原因。

优化建议应包含证据、受影响实例、适用配置版本、待核对原因、建议改法和验收指标，例如同时观察处理周期、返工率及业务结果，避免仅以减少审批节点为目标。

## 9. 接口开发后如何对接

提供接口地址、请求参数说明、认证方式说明、状态映射和一组去敏 JSON 样例即可开始适配；实际凭据通过安全的本地配置传入，不放在文档、示例或聊天中的公开文本里。样例优先覆盖：普通归档单、长期在途单、退回重进、多人会签、代理或转办、暂停后恢复；不存在的情形明确说明。

先核对实例数、报表记录数和原始日志事件数，再验证代理、轮次和耗时解释。首版接口对接完成前，现有工具仍只做离线配置解析，不能宣称已接入线上运行分析。
