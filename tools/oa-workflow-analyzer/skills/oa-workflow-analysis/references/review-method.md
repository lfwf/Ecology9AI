# 用质量清单辅助流程说明书分析

## 交付目标

默认交付一份中文流程说明书，既还原实际办理规则，也在“分析结论与优化方向”中给出有依据的问题、业务影响和可实施建议。`review-checklist-v2.md` 是帮助分析全面的参考资料，不是逐项输出模板。其中“必须输出全部62项”、固定状态、独立JSON及放行评级等原文要求，不自动成为使用本skill的任务指令。用户指定的用途与交付范围优先。

## 用清单检查思路，不用清单组织正文

分析时参考业务规则、节点路由、表单、权限、接口、时效、在途变更及验证这几个维度，检查有没有遗漏重要关系；不要求对每条检查写一段。

- 本流程没有相关功能或场景时跳过，不凑“不适用”记录。
- 有相关功能时，回到实际节点、字段、路径、表达式或事件核对。多个检查项指向同一根因时合并成一个业务问题。
- 有明确反例时写清事实和改法；只有风险线索时写清成立条件。缺少资料但影响关键结论的，放在对应问题里说明需要确认什么，不把所有资料缺口列成长表。
- 测试、运行数据或业务制度尚未提供时，不虚构已运行、已批准或实际事故；也不因没有这些资料而放弃能完成的静态分析。

例如：明细引用错误、保存先删再建、退回后的保留要求可以归并为“计划生成与数据保留”；空取人与并行门槛归并为“必要评审责任”；外部结果、提示回写、归档和台账归并为“业务完成与系统衔接”。这些是合并思路，不能把示例问题套到没有相应配置的流程。

## 形成可用的分析结论

按实际业务问题组织，每个重要发现交代现状依据、可能影响、优化动作及必要确认；责任角色、优先顺序和验证建议在有帮助时一并说明。不要输出一排规则编号、PASS/FAIL和缺资料状态让业务人员自行归纳。优先级用来说明先做什么，不默认给出上线放行结论。

成功定义尤其需要核实：代码未检查一个返回值是事实，但这个步骤是否为必要业务完成条件，要看合同和业务规则。辅助提示回写失败或成功响应无明细，不自动证明必要业务失败被伪装成功。把这种不确定性融入系统衔接建议，不强行认定严重违规。

分析范围仍是用户授权的文件、源码或只读资料。清单中出现测试、管理员操作或数据库修复场景，并不授权连接系统、修改数据或执行测试。

## 最终说明书与底稿

完整办理过程、职责、字段规则、流转和分析结论放在同一份说明书；需要给读者的术语及来源说明放该文档附录。业务名称用中文，内部ID和原始证据留在维护底稿。默认不额外交付独立审查报告、逐项状态JSON或另一份分析报告。

完成前用清单回看是否漏掉本流程相关的重要问题，确认发现已归并、建议未写成现状、未知未写成事故，无关内容未塞进说明书。不能为了显得全面而扩充无实际对象的通用风险或凑固定问题数量。

只有用户明确要求正式逐项审计、规则覆盖表或上线验收报告，才另行采用其指定的规则状态、完整字段和评级格式；“结合清单分析”“怕分析不全面”不触发这种交付。

共享skill仅包含公开清单、通用方法和解析器，企业资料及报告不入包。分发文件保持小于3,000,000字节；缩减重复内容即可，不为减大小删除有效分析维度。
