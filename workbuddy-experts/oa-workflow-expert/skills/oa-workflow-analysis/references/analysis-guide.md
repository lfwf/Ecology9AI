# 流程分析与交付规则

## 从业务控制出发

先回答四件事：谁必须负责；每种业务结果如何继续、补充或结束；后续收到的数据是否可信；满足什么条件才算完成。沿这四条线检查配置与代码的衔接，不能把导出表逐张复述当作分析。

完整流程说明通常同时包含“实际配置如何办理”和“发现什么问题、建议如何优化”。用户只问一个字段、只要路径表或明确暂不分析时，按其范围完成，不扩大任务。没有发现明确问题时，可以说明审查范围和未发现项，不凑问题数量。

使用 [清单辅助分析方法](review-method.md) 和 [v2.0参考清单](review-checklist-v2.md) 在分析时查漏补缺。清单覆盖面不等于交付目录：无关项跳过，同一问题对应多个检查项时合并，相关发现融入同一说明书的“分析结论与优化方向”，不逐项复述清单、不凑62条结论，不默认输出状态表或放行评级。

## 中文业务层与技术证据层

- 正文、图和业务表用实际中文名称及选项含义。例如写“四个必需分支完成后汇合”“评审结果为通过”，而非仅列合并数、字段编号或选项值。枚举未经核对时写明语义未知，不把不同表的相同数字视为同义。
- 内部ID、数据库字段名、配置码、证据编号、XML行号、源码位置保留在工作底稿；需要读者核对的内容放同一本说明书的来源附录。一个名称对应多个字段时，用“初评估算／研发成本／对外报价”等实际阶段区分，底稿保留精确映射，不能把字段合并解释。
- 不从岗位名猜实际办理人。区分固定个人、角色成员、表单人员、历史节点操作者、创建人及抄送。会签不必然多人；抄送不必然审批；对未识别的顺序码不补造顺序。
- 图必须覆盖实际节点、分支及出口，条件和退回另表说明也可。未配置条件的线不能擅自标成通过或否决；不把建议中的新节点画成现有配置。节点或路径合并显示时说明覆盖关系。

## 按适用情况检查

| 维度 | 应核对的关系 | 分析时避免的跳跃 |
| --- | --- | --- |
| 责任与汇合 | 每个必要分支的有效取人、条件参与、会签与合并门槛是否一致 | 空组不证明实际一定卡死，也不授权降低门槛 |
| 决策与出口 | 通过、不通过、补充、客户异议、撤销是否各有明确动作和权限；普通提交是否可能与否决结果不一致 | 条件为空不证明一定同时走两条线；按钮约定也不能自动当成后端控制 |
| 数据与权限 | 基础权限、禁止手改、行操作、模板布置、隐藏及动态联动是否共同支持该阶段职责 | 缺配置、空值、不可见、只读、模板未布置并非同一状态 |
| 金额与公式 | 表达式输入、触发依赖、单位、空值与保存校验；相似字段所处阶段 | 没导出公式不证明业务不会计算；不猜财务口径 |
| 保存与明细 | 保存／提交事件、实际行索引、字段所属表、删除重建、人工记录保留、失败及重复操作 | 源码调用不证明已持久化丢失数据；正常返回后的回调不等于异常后仍继续 |
| 人员维护 | 实际取人与显示字段、复制触发、交接、在途任务和授权替补 | 同一个人经过两个节点不构成双人复核，也不自动是制度违规 |
| 编号与集成 | 外层注册与内部配置、执行顺序、申请关联键、有效业务结果、回写、同步资格与失败恢复 | 动作存在或HTTP成功不证明业务完成；不同时开启全部重复入口 |
| 完成与统计 | 归档原因、批准结果、外部结果、待补偿状态能否区分 | 否决也可能归档，不能用归档数代替成功立项数 |
| 效率与返工 | 必需资料是否能前置补齐；同一版需求、计划与报价是否贯穿；变更后重审范围 | 节点数量不等于耗时，名称相似不证明职责冗余 |

活动与停用布局分别检查。只在停用模板存在的修正代码，不是活动页面已受保护的证据。既分析正常路径，也分析不应继续的条件、空人员、重复保存、删行后索引、超时重试及部分成功的恢复；不用真实写操作验证猜测。

## 把发现写成可以实施的建议

每项重要发现至少交代以下内容；可以用连续段落或表格，不要求固定标题模板：

1. **事实与定位**：哪两个明确配置或代码行为不一致，依据何在。缺资料时准确说明缺少哪项，不把所有缺口都称为漏洞。
2. **可能影响**：在什么条件下影响谁、影响何种业务结果。把推断与已发生的事件分开；不要无证据宣称数据丢失、绕过审核或系统入侵。
3. **优先级及理由**：先处理会破坏数据或必要控制的明确错误，再处理需核实的高影响衔接，之后改善维护与体验。没有运行样本时不按事故频率排序。
4. **具体改法**：说明修改哪一种职责、条件、赋值依赖或结果检查，以及失败时怎样保留、提示和恢复。不能只有“加强管理／优化流程／补资料”。需要业务决定时给出选项与适用条件，不擅自替其批准。
5. **建议负责角色**：业务负责人确认规则，OA、表单或接口维护人实施。明确是建议分工，不虚构组织任职或授权。
6. **验收情形**：给出正向、拒绝、缺失、重复或失败场景的预期结果。验收方案不等于已经执行的测试。
7. **技术证据与限制**：源文件哈希、证据记录、脚本及源码位置，哪些结果仍须线上版本或既有日志验证。

明确错误应提出明确修复，不无限期停留在“建议核实”。取决于平台或业务约定的问题，先界定待确认事项及确认后的处理，不盲改开关。多个问题共享同一根因时可以合并，不能为了凑十项拆碎。

给出少量整改批次或顺序，说明预期产物，例如职责表、结果分流表、财务口径、填写矩阵、集成前提及异常恢复验收。不要许诺未经验证的工期、费用或效率提升百分比，也不把全部节点删除当作效率优化。

## 运行分析的边界

静态资料足以判断配置一致性与代码线索，不足以量化真实卡点。接入用户授权的运行文件或只读接口后，才比较等待分布、在途积压、返工路径、退回原因、分支汇合和接口恢复时间；按实例、节点访问轮次及操作事件区分粒度，避免多人会签和重入导致重复计数。

区分已完成耗时与仍在等待的时长、自然时间与约定工作时间、申请总周期与人员操作时长。事件次数不能直接按人员明细行相加，当前状态表不能替代完整历史。当前授权仅有定义文件时，不索要数据库直连，也不假定运行API已经实现。

## 交付前核对

核对全部节点和路径是否覆盖；关键字段和选择项是否映射；空值、未知与停用是否保留；问题是否有实际依据；建议是否被误写为现状；正文是否仍有不明ID；证据引用是否属于同一源文件哈希并真实存在。保留人工修订前的内容，改正事实错误时记录核对依据。

解析器管理的目录只作读取，人工说明书及底稿另存；办理规则和分析结论放在同一份说明书。PDF应以当前最终文本生成并渲染检查，不只检查抽取文字。最终回复给出这一份说明书和重点判断，必要限制融入相关结论，不另用一套审查报告、原始JSON或待补资料表代替交付。
